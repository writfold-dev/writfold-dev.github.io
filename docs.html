01 / The six steps

One runbook, start to finish

Suppose an agent finds that a service's runbook is out of date. The goal is not to save a summary: it is to keep what was read, check a specific claim, approve a specific edit, and know for certain whether it was applied.

  1. Writfold retains the runbook.

    Pick a named context and keep the runbook's exact bytes, source and revision. Editing the runbook later creates new evidence; it never rewrites what an earlier decision relied on.

    Today: immutable object storage is tested on its own.

  2. Weft assesses a claim about it.

    State what you assume and what you want to check, for example that the service has a recovery plan. Weft reports each check as entailed, refuted or undetermined. It does not read prose or infer facts the theory does not state.

    Today: runs as a standalone tool.

  3. Splicery prepares a change.

    Describe a byte-exact edit, for example correcting one line of the runbook. Splicery computes a candidate file and leaves the original untouched.

    Today: offline preview runs.

  4. You approve that exact change.

    Writfold checks the prepared change against the context's policy, and you sign an approval bound to that change, not to the source or an earlier proposal.

    Today: planned.

  5. Writfold applies it in its own worktree.

    Writfold re-checks that the file still matches what was prepared, then writes the change into a Git worktree it created for this run. No other process holds that write permission.

    Today: worktree creation and staged single-file install are tested on their own.

  6. A receipt makes recovery exact.

    Writfold records a durable receipt. If the response is lost, it finds and returns the same completed change instead of applying it twice.

    Today: planned.

The first release will be an experimental alpha for disposable data you can discard and recreate.

02 / Evidence

What a record keeps

A source can support a statement without making it universally true. Writfold keeps support, contrary evidence, freshness, authority and publication as separate facts.

What a record needs

The exact source identity, the revision and bytes observed, the claim it relates to, and the context it is assessed in.

What it cannot establish

A citation does not approve a change. A successful search does not show that nothing else exists. A link between records is not an inference rule.

Example

“The service has a recovery plan.”

A captured runbook can support that statement. It does not show that a restore ever succeeded; a restore result is separate evidence with its own time and scope.

03 / Contexts

Shared knowledge, explicit boundaries

A named context sets the scope and policy under which knowledge is assessed. It is not a folder that pools every source and permission an agent can reach.

Select deliberately.

A query names the context it needs. Work and personal knowledge do not share evidence or approval just because one person can access both.

Pin the view.

A read is bound to a release, context and time, so a later publication cannot quietly change a read already in progress.

Show uncertainty.

Missing, expired, contradictory and incomplete evidence stays visible. An empty result is not proof that nothing exists.

04 / Scribes · planned

Reading sources without authority

A scribe will be a small program that fetches a source: a repository, a document service or a team tool. Writfold stores what it returns as an immutable record called a writ. Scribes cannot approve, write to the store or choose a context.

  1. SourceRepository or document
  2. ScribeFetches it
  3. WritImmutable copy
  4. ProposalReviewed and approved separately

The scribe runtime and SDK are not released.

05 / Architecture

Local state, one approval boundary

Writfold is a local tool for Linux x86_64 and WSL2, built as a static Rust binary. It is not a hosted service.

Ownership

Writfold owns the knowledge store, the approval policy and every write. Weft and Splicery run as separate tools; their outputs are inputs to Writfold, never permissions. Git and Worktrunk are pinned native dependencies; Writfold creates and owns the worktree an edit lands in.

Agent protocol

Agents talk to writfold serve over stdio with JSON-RPC frames of at most 64 KiB. Today it accepts only initialize and shutdown and refuses every other method with a typed error. The CLI and the protocol will share the same application decisions.

Storage

Omnigraph is the intended storage backend. Its released 0.14.0 failed a branch-relocation test; a source build of upstream PR #1235 now passes that scoped test and is used for development only. Knowledge releases are designed to publish through Git compare-and-swap. A separate Dolt profile exists for disposable integration testing and is never a fallback.

Verification

The engineering model is written in Lean, and its twelve core theorems are proved under stated assumptions. Selected Rust function bodies are checked with Verus, and concurrency is modelled in TLA+. Tests and agreement between these do not by themselves prove that the Rust code matches the Lean model; the status page lists what each covers.
