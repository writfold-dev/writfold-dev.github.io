This page explains the edit trial: a harness underneath a coding agent that keeps evidence, conclusions, approval and change apart, and records each step. It still runs, as a frozen working demo. 01 / The harness

Underneath the agent, not instead of it

A coding agent such as Claude Code or Codex keeps its own loop: it reads, plans and proposes. Writfold is the layer it goes through for evidence it relies on and for every change to your files. This runs today as a cooperating single-user trial, now a frozen working demo; the status page lists what is and is not built.

Know: Tuft finds, Writfold retains.

What the agent relies on is kept as exact bytes of a file at a full commit id, bound as a citation by digest. Tuft finds exact text or a bounded regex in one pinned commit and retains the hits the same way. A Weft report that cites anything not retained is refused.

Conclude: Weft checks the plan.

The claims a plan depends on are stated against declared assumptions and cited evidence. Weft reports each as entailed, refuted or still open; it never grants permission. Writfold records Weft's results as hypothetical, and an approval can require named checks to be entailed.

Change: Splicery prepares, Writfold applies.

Splicery expresses the edit as a byte-exact recipe and previews the candidate. Writfold applies it only in a Git worktree it created and owns, under your signed approval and a current operator grant.

Record: every step leaves evidence.

A validated ledger lets a run be reviewed afterwards and recovered after an interrupted apply. A later session can read retained evidence back, verified against its digest.

Who does what

The agent proposes. Writfold decides and records.

The agent and the model stay yours. Weft and Splicery only read and propose; their outputs are inputs to Writfold, never permissions. Only Writfold writes, and only where it owns the worktree.

02 / The six steps

One runbook, start to finish

Suppose an agent finds that a service's runbook is out of date. The goal is not to save a summary: it is to keep what was read, check a specific claim, approve a specific edit, and know for certain whether it was applied.

  1. Writfold retains the runbook.

    Keep the runbook's exact bytes, source and revision. Editing the runbook later creates new evidence; it never rewrites what an earlier decision relied on.

    Today: runs in the trial profile. writfold trial retain, or Tuft's retain, keeps the exact bytes of a file range at a full commit id (refs, abbreviations and HEAD are refused) and binds them as a writfold-citation/1 citation; equal text at two positions is two citations. Named contexts are designed, not built.

  2. Weft assesses a claim about it.

    State what you assume and what you want to check, for example that the service has a recovery plan. Weft reports each check as entailed, refuted or undetermined. It does not read prose or infer facts the theory does not state.

    Today: runs as a standalone tool. In the trial, prepare --report binds a complete Weft report and refuses one that cites evidence that was not retained or no longer matches its digest; approve --require CHECK refuses unless each named check is entailed. That gate is proved over the shipped Rust. Weft's results are recorded as hypothetical.

  3. Splicery prepares a change.

    Describe a byte-exact edit, for example correcting one line of the runbook. Splicery computes a candidate file and leaves the original untouched.

    Today: offline preview runs. In the trial, prepare replays the recipe through the pinned Splicery kernel in Writfold's own sparse worktree, and refuses a candidate identical to its source.

  4. You approve that exact change.

    Writfold checks the prepared change against the context's policy, and you sign an approval bound to that change, not to the source or an earlier proposal.

    Today: runs in the trial profile. writfold trial approve signs an approval bound to the prepared change and checks it against the current grant; the grant and revocation decisions are proved over the shipped Rust. There is no revocation command yet.

  5. Writfold applies it in its own worktree.

    Writfold re-checks that the file still matches what was prepared, then writes the change into a Git worktree it created for this run. It never writes your own checkout.

    Today: runs in the trial profile, in a sparse worktree Writfold created, after re-checking the approval, the grant and the file. The trial is cooperating: it does not stop an agent's own shell from writing elsewhere. The hardened Worktrunk path is tested on its own, not connected.

  6. A record makes recovery exact.

    Writfold records a durable claim before it writes and one outcome after. If the apply is interrupted, it decides what happened from the file's bytes instead of applying the change twice.

    Today: in the trial profile, the claim and outcome live in a validated ledger kept in a local Git repository. writfold trial recover settles an interrupted apply: applied exactly when the file holds the candidate's bytes, abandoned exactly when it holds the source's, otherwise unknown, for a person to resolve. The ledger and recovery decisions are proved over the shipped Rust. Receipts beyond the trial ledger are planned.

Today's release is a source-only preview, v0.1.0-dev.1: a cooperating single-user trial. Try it on repositories and data you can discard and recreate.

03 / Evidence

What a record keeps

A source can support a statement without making it universally true. Writfold keeps support, contrary evidence, freshness, authority and publication as separate facts.

What a record needs

The exact source identity, the revision and bytes observed, the claim it relates to, and the context it is assessed in.

What it cannot establish

A citation does not approve a change. A successful search does not show that nothing else exists. A link between records is not an inference rule.

Example

“The service has a recovery plan.”

A captured runbook can support that statement. It does not show that a restore ever succeeded; a restore result is separate evidence with its own time and scope.

04 / Contexts

Shared knowledge, explicit boundaries

A named context sets the scope and policy under which knowledge is assessed. It is not a folder that pools every source and permission an agent can reach. Contexts are designed, not built: the trial uses one state directory with one operator key.

Select deliberately.

A query names the context it needs. Work and personal knowledge do not share evidence or approval just because one person can access both.

Pin the view.

A read is bound to a release, context and time, so a later publication cannot quietly change a read already in progress.

Show uncertainty.

Missing, expired, contradictory and incomplete evidence stays visible. An empty result is not proof that nothing exists.

05 / Architecture

Local state, one approval boundary

Writfold is a local tool for Linux x86_64 and WSL2, built as a static Rust binary. It is not a hosted service.

Ownership

Writfold owns the knowledge store, the approval policy and every write. Weft and Splicery run as separate tools; their outputs are inputs to Writfold, never permissions. Tuft runs inside Writfold. Git is a native dependency; the trial creates its worktrees with Git directly, and the hardened path uses pinned Worktrunk. Either way Writfold creates and owns the worktree an edit lands in.

Agent protocol

The agent keeps its own loop and reaches Writfold through writfold serve: JSON-RPC 2.0 over stdio with frames of at most 64 KiB. A session that negotiates writfold.trial/1 can call trial/show, trial/retain, trial/prepare, trial/run, trial/evidence-list and trial/evidence-show, each through exactly the function the CLI calls. The Weft binary trial/run uses is fixed when the server starts (writfold serve --weft), never named by the client. Approve, apply and recover stay CLI-only and answer Method not found over serve: approval is the operator's step, not an agent-session method. MCP is not implemented.

Storage

Since 11 November, the plan is Git as the source of truth, plus a local index that can always be rebuilt from it, with fuzzy (typo-tolerant) text search planned in that index. None of it is built yet. The trial keeps its ledger in a local Git repository, and Tuft reads one pinned Git commit. Earlier work behind one swappable storage boundary is paused. For Dolt, exact pinned reads and exact, prefix and substring lookups pass a 13-check conformance suite against a real disposable Dolt database, and a conditional single writer and a first publication path are tested on their own. For Omnigraph, the released 0.14.0 failed a branch-relocation test, a source build of upstream PR #1235 passed that scoped test and was used for development only, and Omnigraph was never admitted.

Verification

The engineering model is written in Lean. The ledger, grant, revocation, recovery-outcome, required-check and edit-flow decisions are proved over the shipped Rust, selected domain bodies are checked with Verus, and concurrency is modelled in TLA+. The rest of the Rust is tested, not proved. How we know explains each layer.

06 / How we know

Specified, proved, tested, measured

Each claim on this site rests on one of these layers. Only the kernels named below are proved over the code that ships; everything else is tested or measured, and the design is a design.

  1. Specify: the Lean calculus.

    The engineering model and its twelve core theorems, proved in Lean under stated assumptions. It says what the system should guarantee, not what the Rust does.

  2. Prove: the shipped kernels.

    Small pure decision kernels are translated from the Rust to Lean 4 by Charon and Aeneas. The translation is committed and checked for drift, and the theorems state, for every input, that each function terminates without failing and returns exactly what its specification says. Production calls exactly the translated code. Each theorem's axioms are audited, and deliberately broken copies of the Rust must each break their named theorem: all 20 of Writfold's semantic mutants are rejected.

  3. Cross-check: cases from the model.

    Cases exported from the Lean calculus must give the same answers in Rust: 31 ledger steps and 79 grant steps, which now run through the proved kernels, and 39 procedure cases.

  4. Test: everything else.

    Rust tests against real Git and storage, deliberately broken variants the tests must catch, Verus-checked identity and quantity bodies, TLA+ models of concurrent behaviour, and an adversarial campaign against the real trial CLI (below).

Measured: latency

Agents call these operations many times per task, so every agent-facing operation has a budget: 1 s at p95, with a hard 5 s ceiling. Not yet

  • No project continuity verbs and no fuzzy search yet; both are planned. The Dolt and Omnigraph backends are paused.
  • No profile that stops an agent writing outside Writfold: the trial is cooperating.
  • No measured token win: all five token pilots used more tokens than ordinary tools (raw data).
  • Not proved: the append success shape, the edit-flow validator, procedure checking and the domain adapters.

Trust base: the Charon/Aeneas translation, the Aeneas library's models of the Rust operations used, the Lean kernel and Lean's three standard axioms. The kernel specifications mirror the calculus but are not yet machine-linked to it, and none of this makes Writfold as a whole a verified product. Writing the proofs found one real defect: an integer-overflow edge in the ledger's sequence check, now fixed. Details: Writfold, Weft, Splicery.
