The intended vertical path

Keep the handoffs inspectable.

Take a runbook as an example. The goal is not simply to save a summary: it is to retain what was read, assess a specific claim, authorize a specific edit and recover its result reliably. This complete owner-backed path is not implemented yet.

  1. Writfold retains the inputs.

    Choose a named context and keep the exact runbook bytes, source identity and revision. An edited source must not replace the evidence used for an earlier decision.

  2. Weft assesses the declared theory.

    Evaluate the proposal's logical obligations under explicit assumptions. The current symbolic engine can distinguish entailment, refutation and unresolved outcomes; it does not infer arbitrary facts from prose or authorize a write.

  3. Splicery prepares the change.

    Prepare a bounded edit for review from the assessed proposal. Preparation describes the intended change; it neither grants approval nor silently applies the edit.

  4. Writfold authorizes the effect.

    Check the prepared edit against the named context's policy and required signed approval. Approval must bind the actual change, not merely the source or a previous proposal.

  5. Writfold's native adapter materializes it.

    Apply the authorized edit to the exact run-owned worktree while retaining its reservation and checking current preconditions. This filesystem effect is distinct from publishing a knowledge release in the structured store.

  6. A durable receipt makes recovery explicit.

    Retain the result so that losing the response does not mean losing knowledge of the effect. Recovery must identify and return the same completed effect, not apply it again. This behavior still needs implementation and end-to-end qualification.

For the experimental alpha, use only disposable data that you can discard and recreate. No production data support, automatic backend fallback or relaxed safety gates.

01 / Evidence

Keep the source. Keep the distinction.

A source may support a statement without making that statement universally true. Writfold's model keeps support, contrary evidence, freshness, validation, authority and publication separate.

What a record needs

Exact source identity, the revision and bytes observed, the claim it relates to, and the context in which it is assessed. A later edit at the same URL must not silently become the evidence for an earlier decision.

What it cannot establish

A citation alone does not approve a change. A successful retrieval does not demonstrate complete coverage. A database relationship is not an inference rule.

Illustrative example

“The service has a recovery plan.”

A captured runbook can support that statement. It does not prove a restore was performed successfully. A restore result is separate evidence, with its own scope, time and identity.

This is an explanation of the model, not an observation about a real service.

02 / Contexts

Shared knowledge. Explicit boundaries.

A named context specifies the scope and policy under which knowledge is assessed. It is not a folder that silently combines every source or permission available to an agent.

Select deliberately.

A query names the context it needs. Work and personal knowledge do not pool evidence or approval just because the same person can access both.

Pin the view.

The intended retrieval contract binds a release, context and assessment time. Later publication must not quietly change an in-progress historical read.

Show uncertainty.

Missing, expired, contradictory and incomplete evidence remain visible. An empty result is not automatically proof that nothing exists.

03 / Scribes · planned

Acquisition without authority.

Scribes are the planned integration boundary for small source-reading programs. Their job is to acquire evidence, not to sign approvals, mutate the knowledge store or choose an authorization context.

  1. SourceRepository or document
  2. ScribeBounded acquisition
  3. WritImmutable evidence record

The scribe runtime, plugin SDK and catalog workflow are not released. There are no installation instructions for them yet.

04 / Architecture direction

Local state. One approval boundary.

The active target is Linux x86_64 and WSL2. Writfold is a local tool in development, not a hosted knowledge service.

Owner & authority

Writfold

Writfold owns the knowledge workflow: retained inputs, context policy, authorization and the orchestration of owner effects and receipts. Its current Rust runtime initializes and shuts down; the complete owner data and effect services are not implemented.

Assessment & preparation

Weft & Splicery

Weft provides assessment; Splicery prepares edits. Their control and local artifact paths provide development evidence, not permission to mutate Writfold data. Writfold's authorization boundary remains separate.

Intended structured backend

Omnigraph

We are evaluating a pinned source build of the upstream relocation fix as a development unblocker. Its storage contract RFC and implementation are not yet merged; local admission must establish exact retained history and independent restore before integration relies on it.

Separate development scope

Dolt & discovery

Typed Dolt reads and signed-input components exist for isolated disposable integration realms. Further Dolt-specific alpha work is paused while the Omnigraph candidate is evaluated. There is no automatic fallback. Fuzzy discovery and integrated reading views remain unavailable.

A backend commit does not itself authorize a Writfold change. Choosing a disposable alpha does not close the original safety or qualification gates, establish production durability, or provide a supported migration path for production data.

05 / Status & assurance

Real exercises. A bounded claim.

The current development record covers 12 real-process scenarios, 29 invocations and 8 coverage admission tests. These counts describe exercised control and local artifact paths, not a released end-to-end knowledge engine.

What exists today

Rust domain and wire foundations, process control and local artifact paths, typed Dolt reads, and supplied signed-approval components. The Writfold runtime itself currently initializes and shuts down.

What those exercises do not prove

Owner data/effect services, native materialization, durable receipts and same-effect recovery after response loss remain unimplemented in the complete Writfold workflow. The reported counts do not establish these capabilities, installed-toolchain readiness or production safety.

What comes next

Qualify the exact native storage candidate, complete the shared input-to-receipt path, then exercise clean installation and recovery. Source-built development use is distinct from an approved public alpha dependency. Existing safety gates stay in force.

Availability

Under development, not alpha-ready.

The approved direction is a public experimental disposable alpha. This guide does not advertise an installer or qualified release. Do not use production data; no production data support is offered.

The earlier kctx reference is public historical Python/Lean source, not the released Rust product.

Installation instructions must match an actual pinned artifact and its exercised limits. Website publication alone is not product qualification.
