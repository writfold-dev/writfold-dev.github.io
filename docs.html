How it works

The record behind
the context.

Writfold is designed as a harness underneath a coding agent: it governs what the agent may know, conclude and change, and records each step. This page explains how, and how the pieces fit together.

Two worked examples run today: a Weft assessment of a small set of claims, and a Splicery edit of a small Rust file. Unfamiliar terms are in the glossary.

01 / The harness

Underneath the agent, not instead of it

A coding agent such as Claude Code or Codex keeps its own loop: it reads, plans and proposes. Writfold is the layer it goes through for knowledge it relies on and for every change to your files. This is the design; today only the pieces listed on the status page run.

Know: Writfold retains evidence.

What the agent read is kept as exact bytes with its source and revision, inside a named context. Answers cite that retained evidence, not a summary or a live URL.

Conclude: Weft checks the plan.

The claims a plan depends on are stated against declared assumptions and evidence. Weft reports each as entailed, refuted or still open; it never grants permission.

Change: Splicery prepares, Writfold applies.

Splicery expresses the edit as a byte-exact recipe and previews the candidate. Writfold applies it only in a Git worktree it created and owns, under your signed approval and a current operator grant.

Record: every step leaves evidence.

Receipts let a run be reviewed afterwards, recovered after a lost response, and reused by the next session.

Who does what

The agent proposes. Writfold decides and records.

The agent and the model stay yours. Weft and Splicery only read and propose; their outputs are inputs to Writfold, never permissions. Only Writfold writes, and only where it owns the worktree.

02 / The six steps

One runbook, start to finish

Suppose an agent finds that a service's runbook is out of date. The goal is not to save a summary: it is to keep what was read, check a specific claim, approve a specific edit, and know for certain whether it was applied.

  1. Writfold retains the runbook.

    Pick a named context and keep the runbook's exact bytes, source and revision. Editing the runbook later creates new evidence; it never rewrites what an earlier decision relied on.

    Today: immutable object storage is tested on its own.

  2. Weft assesses a claim about it.

    State what you assume and what you want to check, for example that the service has a recovery plan. Weft reports each check as entailed, refuted or undetermined. It does not read prose or infer facts the theory does not state.

    Today: runs as a standalone tool.

  3. Splicery prepares a change.

    Describe a byte-exact edit, for example correcting one line of the runbook. Splicery computes a candidate file and leaves the original untouched.

    Today: offline preview runs.

  4. You approve that exact change.

    Writfold checks the prepared change against the context's policy, and you sign an approval bound to that change, not to the source or an earlier proposal.

    Today: runs in the trial profile. writfold trial approve signs an approval bound to the prepared change and checks it against the current grant; the grant decision is proved over the shipped Rust.

  5. Writfold applies it in its own worktree.

    Writfold re-checks that the file still matches what was prepared, then writes the change into a Git worktree it created for this run. No other process holds that write permission.

    Today: runs in the trial profile, in a worktree Writfold created, after re-checking the approval, the grant and the file. The hardened Worktrunk path is tested on its own, not connected.

  6. A receipt makes recovery exact.

    Writfold records a durable receipt. If the response is lost, it finds and returns the same completed change instead of applying it twice.

    Today: in the trial profile, a durable claim is recorded before each install and one outcome after it, in a validated ledger kept in a local Git repository; writfold trial recover settles an interrupted apply. The ledger decision is proved over the shipped Rust. Receipts beyond the trial ledger are planned.

The first release will be an experimental alpha for disposable data you can discard and recreate.

03 / Evidence

What a record keeps

A source can support a statement without making it universally true. Writfold keeps support, contrary evidence, freshness, authority and publication as separate facts.

What a record needs

The exact source identity, the revision and bytes observed, the claim it relates to, and the context it is assessed in.

What it cannot establish

A citation does not approve a change. A successful search does not show that nothing else exists. A link between records is not an inference rule.

Example

“The service has a recovery plan.”

A captured runbook can support that statement. It does not show that a restore ever succeeded; a restore result is separate evidence with its own time and scope.

04 / Contexts

Shared knowledge, explicit boundaries

A named context sets the scope and policy under which knowledge is assessed. It is not a folder that pools every source and permission an agent can reach.

Select deliberately.

A query names the context it needs. Work and personal knowledge do not share evidence or approval just because one person can access both.

Pin the view.

A read is bound to a release, context and time, so a later publication cannot quietly change a read already in progress.

Show uncertainty.

Missing, expired, contradictory and incomplete evidence stays visible. An empty result is not proof that nothing exists.

05 / Scribes · planned

Reading sources without authority

A scribe will be a small program that fetches a source: a repository, a document service or a team tool. Writfold stores what it returns as an immutable record called a writ. Scribes cannot approve, write to the store or choose a context.

  1. SourceRepository or document
  2. ScribeFetches it
  3. WritImmutable copy
  4. ProposalReviewed and approved separately

The scribe runtime and SDK are not released.

06 / Architecture

Local state, one approval boundary

Writfold is a local tool for Linux x86_64 and WSL2, built as a static Rust binary. It is not a hosted service.

Ownership

Writfold owns the knowledge store, the approval policy and every write. Weft and Splicery run as separate tools; their outputs are inputs to Writfold, never permissions. Git and Worktrunk are pinned native dependencies; Writfold creates and owns the worktree an edit lands in.

Agent protocol

The agent keeps its own loop and is designed to reach Writfold through writfold serve over stdio with JSON-RPC frames of at most 64 KiB. Today it accepts only initialize and shutdown and refuses every other method with a typed error. The CLI and the protocol will share the same application decisions.

Storage

Omnigraph is the intended storage backend. Its released 0.14.0 failed a branch-relocation test; a source build of upstream PR #1235 now passes that scoped test and is used for development only. Knowledge releases are designed to publish through Git compare-and-swap. A separate Dolt profile exists for disposable integration testing and is never a fallback.

Verification

The engineering model is written in Lean. The ledger and grant decisions are proved over the shipped Rust, selected domain bodies are checked with Verus, and concurrency is modelled in TLA+. The rest of the Rust is tested, not proved. How we know explains each layer.

07 / How we know

Specified, proved, cross-checked, tested

Each claim on this site rests on one of four layers. Only the kernels named below are proved over the code that ships; everything else is tested, and the design is a design.

  1. Specify: the Lean calculus.

    The engineering model and its twelve core theorems, proved in Lean under stated assumptions. It says what the system should guarantee, not what the Rust does.

  2. Prove: the shipped kernels.

    Small pure decision kernels are translated from the Rust to Lean 4 by Charon and Aeneas. The translation is committed and checked for drift, and the theorems state, for every input, that each function terminates without failing and returns exactly what its specification says. Production calls exactly the translated code. Each theorem's axioms are audited, and deliberately broken copies of the Rust must each break their named theorem.

  3. Cross-check: cases from the model.

    Cases exported from the Lean calculus must give the same answers in Rust: 31 ledger steps and 79 grant steps, which now run through the proved kernels, and 39 procedure cases.

  4. Test: everything else.

    Rust tests against real Git and storage, deliberately broken variants the tests must catch, Verus-checked identity and quantity bodies, and TLA+ models of concurrent behaviour.
