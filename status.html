02 / Blocked

What cannot run yet

The combined test run of 6 November passed 12 scenarios across 29 invocations, plus 8 coverage tests. Four scenarios need services that do not exist yet, so they are recorded as blocked rather than passed:

  • Persistent handoff of citations, assessments and artifacts between the tools
  • Approved worktree edits replayed through the pinned Splicery kernel
  • Recovery after a crash, when the outcome of an edit is unknown
  • Session benchmarks with retained evidence

The trial profile now approves, applies and recovers edits within its own cooperating scope. These scenarios stay blocked until the hardened services run them.

03 / Verification

How progress is measured

The design defines 32 gates that a full release must pass, and a smaller set of 14 requirements for the experimental alpha. None has passed yet. Each tested part keeps a record of the exact source, tools and inputs it ran against.

Lean calculus

The engineering model and its twelve core theorems, proved under stated assumptions. The specification.

Proved over the shipped Rust

Writfold's ledger and grant decisions, Weft's set and verdict decisions and Splicery's edit rendering, translated to Lean by Charon and Aeneas and proved for every input. Production calls exactly that code.

Cross-checks and tests

Cases exported from Lean that Rust must agree with, Verus-checked identity and quantity bodies, Rust tests, deliberately broken variants that tests and proofs must catch, and TLA+ models of concurrent behaviour.

Trust base for the proofs: the Charon/Aeneas translation, the Aeneas library's models of the Rust operations used, the Lean kernel and Lean's standard axioms. Everything outside those kernels is tested, not proved, and the kernel specifications are not yet machine-linked to the calculus. How we know lists each kernel.

04 / Next

Road to the experimental alpha

Done in the trial profile: a durable, validated ledger with grants, and prepare, approve, apply and recover through the CLI. Not built: evidence retrieval, citations, receipts beyond the trial ledger and reuse across sessions.

  1. The hardened edit path

    Move the trial flow onto Worktrunk worktrees and the agent protocol, with the same approval, claim and outcome records.

  2. More proved kernels

    Prove revocation, then move the edit-flow validator and procedure checking into the proved kernel.

  3. Clean install and recovery

    Install from a pinned artifact and test recovery end to end, with disposable data only.

05 / Changelog

What changed

  1. 9 Nov 2026

    Decision kernels proved over the shipped Rust with Charon/Aeneas and Lean 4: Writfold's ledger and grant authority (51 theorems), Weft's set algebra, verdict classification and reuse comparison, and Splicery's edit rendering. Every deliberately broken copy of each kernel breaks its named theorem. The proofs found and fixed an integer-overflow edge in the ledger's sequence check. Splicery's Verus proofs for that kernel were retired in favour of these.

  2. 9 Nov 2026

    First connected flow: writfold trial prepares a Splicery edit in Writfold’s own worktree of any Git repository, signs a grant and approval, and applies the edit only after re-verifying them and the file. Every step is recorded in a durable, kernel-validated ledger stored in Git. A cooperating single-user trial profile, not the hardened alpha path.

  3. 8 Nov 2026

    Repositories made public. First agent edit pilot published, with no measured win yet. Signed operator grants and revocations, and a current-grant check that agrees with the Lean model on 79 exported steps. 06 / FAQ

Common questions

Can I use Writfold with my agent today?

Only as a trial. An agent can run writfold trial from its shell to prepare, approve and apply edits in Writfold's own worktree, as in the pilots above, on disposable data. Evidence retrieval, citations and the agent protocol for edits are not built; writfold serve only starts and ends a session.

Does it replace my coding agent?

No. The agent keeps its own loop and model. Writfold is designed as the layer it goes through for retained evidence and for every change to your files.

Is it an MCP server?

Not today. Writfold speaks its own stdio JSON-RPC profile, writfold.agent/1. MCP is not implemented.

Does it need a database?

The intended backend is Omnigraph, run locally as a companion process. There is no hosted service and no account.

What data can I use?

The first release will be an experimental alpha for disposable data only: data you can delete and recreate.

Is the source available?

Yes. The Writfold, Weft and Splicery repositories are public, and this website is public under the MIT license. There are no release binaries yet. The predecessor, kctx, is public.

How does it relate to kctx?

Writfold is kctx's Rust successor. kctx's Python and Lean history is preserved and used as the compatibility reference.

Why Rust, Lean, Aeneas and Verus?

Rust gives a single static binary. Lean states the model and proves its core properties. Aeneas translates small Rust decision kernels to Lean so they can be proved as shipped. Verus checks selected Rust function bodies against their contracts.

Is Writfold formally verified?

No, not as a whole. A few decision kernels are proved over the shipped Rust, listed on How it works. Everything else is tested, and much of the harness is still a design.
