02 / Blocked

What cannot run yet

The combined test run of 6 November passed 12 scenarios across 29 invocations, plus 8 coverage tests. Four scenarios need services that do not exist yet, so they are recorded as blocked rather than passed:

  • Persistent handoff of citations, assessments and artifacts between the tools
  • Approved worktree edits replayed through the pinned Splicery kernel
  • Recovery after a crash, when the outcome of an edit is unknown
  • Session benchmarks with retained evidence

The trial profile now retains citations, binds Weft reports, and approves, applies and recovers edits within its own cooperating scope. These scenarios stay blocked until the hardened services run them.

03 / Verification

How progress is measured

The design defines 32 gates that a full release must pass, and a smaller set of 14 requirements for the first experimental release on disposable data. None has passed yet; the preview rests on scoped component evidence. Each tested part keeps a record of the exact source, tools and inputs it ran against.

Lean calculus

The engineering model and its twelve core theorems, proved under stated assumptions. The specification.

Proved over the shipped Rust

Writfold's ledger, grant, revocation, recovery-outcome, required-check and edit-flow decisions, Weft's set and verdict decisions and Splicery's edit rendering, translated to Lean by Charon and Aeneas and proved for every input. Production calls exactly that code. All 20 of Writfold's semantic mutants are rejected.

Cross-checks, tests and measurements

Cases exported from Lean that Rust must agree with, Verus-checked identity and quantity bodies, Rust tests, deliberately broken variants, TLA+ models of concurrent behaviour, an adversarial campaign against the real CLI (8 of 8 cases as expected) and a latency budget (1 s p95, 5 s ceiling) that every trial operation meets.

Trust base for the proofs: the Charon/Aeneas translation, the Aeneas library's models of the Rust operations used, the Lean kernel and Lean's standard axioms. Everything outside those kernels is tested, not proved, and the kernel specifications are not yet machine-linked to the calculus. How we know lists each kernel.

Measurements

Latency and agent pilots

We publish measurements as they come, including results that do not favour us. Every agent-facing operation is budgeted at 1 s p95 with a 5 s ceiling; on a 100,000-file repository every trial operation's p95 is under 0.5 s, and through serve the p95 is 27 ms for retain, 166 ms for prepare and 53 ms for show (tables). The agent pilots below use six precise-edit tasks, one Sonnet agent per task and arm, graded byte for byte against hidden expected files. One repeat per cell: debug pilots, not headline results.

Correctness was equal in both pilots, and the Writfold flow cost about 16% more tokens: there is no token win yet. What it adds is structural: the agent never wrote the checkout, and every applied edit carries a verified approval and a recorded outcome. In one task the agent’s first preparation would have joined two lines; it was never approved, a corrected one was applied, and the rejected one never touched a file. In these pilots the agent approved its own edits, so they measure mechanics and overhead, not human review; approval has since become CLI-only for serve sessions.

The projection pilot compared Tuft with grep-and-read on six evidence-finding tasks (two repeats each, same model). Correctness was 12/12 in both arms, and the Tuft arm used 5.3% more tokens, more on every task. The tasks had 1 to 9 matches, so Tuft's budget and omissions never came into play. Agents also retyped Tuft's quoted rows by hand where grep output could be piped, and Tuft's headers and byte ranges roughly doubled the tool output. A second projection pilot used lean compact output and tasks with up to 297 matching lines: correctness was again 12/12 in both arms, and the Tuft arm used 3.1% more tokens, more on all six tasks. Its tool output was 5.6% smaller, but agents wrote longer programs and made more calls, and grep pipelines already kept the other arm's output small. So Tuft's typed output costs about the same as grep: within 3.1% of grep's tokens, Tuft gives search pinned to one commit, a completeness signal (coverage, omissions, cursor) and retained citations a Weft report and an approval can bind to. It does not save tokens on lookups a shell pipeline can reduce. Raw data: projection pilot 2, projection pilot, trial-flow pilot, edit pilot.

04 / Next

What comes next

Done in the trial profile: a durable, validated ledger with grants; retain, prepare, approve, apply and recover through the CLI; show, retain and prepare through serve; Tuft v0. Not built: semantic or fuzzy search, a live knowledge service, Dolt writes, named contexts, receipts beyond the trial ledger and reuse across sessions.

  1. One run file

    Tuft finds evidence, Weft checks it and Splicery prepares the edit in one command, all bound by digest. Approval stays a separate CLI step.

  2. More models and proofs

    A TLA+ model of the trial stream (apply, recover, an external writer and crash points), then the edit-flow validator moved into the proved kernel.

  3. Storage

    A native Dolt conditional writer behind the same boundary, and Omnigraph once it is admitted.

06 / FAQ

Common questions

Can I use Writfold with my agent today?

As a cooperating single-user trial. An agent can run writfold trial and writfold tuft run from its shell, or call show, retain and prepare through writfold serve; approval stays with the operator's CLI. Writfold never writes your checkout, but in this trial nothing stops the agent's own shell from doing so.

Does it replace my coding agent?

No. The agent keeps its own loop and model. Writfold is designed as the layer it goes through for retained evidence and for every change to your files.

Is it an MCP server?

Not today. Writfold speaks its own stdio JSON-RPC profile, writfold.agent/1, with the writfold.trial/1 capability. MCP is not implemented.

Does it need a database?

Not for the trial: it keeps its ledger in a local Git repository. Omnigraph, run locally as a companion process, is the target backend; until it is admitted, Dolt is the interim backend behind a swappable boundary, with a conditional single writer but no publication path yet. There is no hosted service and no account.

What data can I use?

Use the preview on repositories and data you can delete and recreate. It is a cooperating trial for one user: it assumes nobody races it on its worktree and that the repository is not hostile.

Does it reduce token use?

Not as a measured win. In all five pilots the Writfold or Tuft arm used more tokens than ordinary tools, with equal correctness: 16% more for the trial flow, 5.3% and 3.1% more for Tuft projections, and 1.7% more for reading retained evidence back in a later session. With lean output, Tuft's typed, pinned and citable results cost within about 3% of plain grep.

Is the source available?

Yes. The Writfold, Weft and Splicery repositories are public, and this website is public under the MIT license. The v0.1.0-dev.1 tag is a source-only preview; there are no release binaries.

Why Rust, Lean, Aeneas and Verus?

Rust gives a single static binary. Lean states the model and proves its core properties. Aeneas translates small Rust decision kernels to Lean so they can be proved as shipped. Verus checks selected Rust function bodies against their contracts.

Is Writfold formally verified?

No, not as a whole. A few decision kernels are proved over the shipped Rust: the ledger, grant, revocation, recovery-outcome, required-check and edit-flow decisions, plus Weft's and Splicery's kernels, listed on How it works. Everything else is tested or measured, and much of the harness is still a design.
