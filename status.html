02 / Roadmap

Done, next, and not planned

The run graph as built is in the run graph guide.

  1. The four questions

    Read and write verbs, the index, pinned citations and the Claude Code plugin. Done

  2. Runs with gates, edits and drafts

    Receipts, statements, Splicery edits, Tuft citations, delivery drafts and watch. Done

  3. Instruction gates and your own delivery modes

    A gate can point to written instructions and ship its script; a mode such as a commit message lists its gates. Done

  4. The run graph, splicing and required steps

    plan set | use | status | advance | skip; required steps checked against the run’s own records. Done

  5. Hooks that show the plan

    The plan position at session start and after compaction, with an inbox. No model in a hook. Done

  6. Proofs, proposals and the closing step

    Proofs of the plan and gate kernels, a TLC model of the run graph, kb check, proposals, the evaluation skill, and Weft assessments of plan steps. Done

  7. Guard rules, checklists and citation kinds

    Rules that deny a command until gates are met, checklist gates covered item by item, per-kind citation lifetimes, and concluded investigations. Done

  8. Checks against systems outside Git

    A command that checks a citation Writfold cannot check from Git, such as a tracker item’s state, with cached results and receipts. Planned

  9. One week of real use

    Count what the checks caught, and what was waived, before adding more. Next

  10. A delivery mode as a step’s gate

    A plan step that owes a checked draft. Planned

  11. Trailer and tracker edges, and --at

    Links read from commit trailers and tracker references, and answers as of a given commit. Planned

  12. An MCP server

    Deferred until a harness without a shell needs one. The CLI and the plugin are the interface. Deferred

  13. A governed profile

    Authority levels, exception routes and signing. Writfold stays single user with cooperating agents. Not planned

04 / FAQ

Common questions

Can I use Writfold today?

Yes, as a preview: download the binary and install the plugin. Single user, cooperating agents, local clones only, Linux x86_64 or WSL2.

Does it need a server or a database?

No. One static binary, records in Git, and a local index that Writfold derives and can always rebuild.

Does Writfold run or schedule my agent?

No. It records the plan and what met each gate. The agent reads the current step, does the work its own way and asks to advance. No hook runs a model.

Can an agent skip a gate or a step?

Yes. Gates and steps record what was checked and report whether it still holds; on their own they block nothing. A gate that was never run shows as open, a skipped step shows as skipped with a reason and a name, and the plan is complete only when every step is done or skipped. A guard rule you add can deny or ask about a command such as git commit until the gates are met; it is a guard, not enforcement, and only sees the tool calls Claude Code shows it.

Is it formally verified?

In part. Three decision kernels are proved in Lean over an Aeneas translation of the Rust that ships. The run graph: a step is recorded as done exactly when it is the current step and every gate is met; a splice keeps every existing step, and repeating it changes nothing. Gate obligations: only exit status 0 on bytes that did not move is a pass, and an attestation or a waiver never counts as satisfied. The Weft assessed gate: a hypothetical entailment never passes. The proof check audits 54 claims across all proved kernels and requires each of 45 mutants of the Rust source to break its named theorem. The rest is tested, not proved: template and gate parsers, the fold from event files to steps, file and Git reads, and scope globs. The write protocol and the run graph are model-checked, not proved (next answer). The proofs trust the Charon and Aeneas translation and the Lean kernel. Details are in the assurance guide.

What did model checking cover?

Two TLA+ models, checked with TLC at small bounds. The write protocol: five invariants over about 18 million states, with a power loss at any moment. The run graph, spec/RunGraph.tla: two runs finished with no violation, two merging clones without drift or a crash (about 2.1 million states) and two sessions in one clone with drift and a crash (about 44 million states). The widest run, two merging clones with drift and a crash, was stopped unfinished at depth 21 with no violation found, so that case is checked only to that depth. Ten mutants of the run-graph model each fail their property. The models are hand-written evidence about the design, not a refinement of the Rust; tests tie them to the code. The run-graph model found two gaps, both now fixed in the Rust: a plan write re-checks its decision under the write lock and refuses if the plan changed, and after a merge plan status, resume and kb check flag !out-of-order, !two-plans and !repeated without changing the plan. Details are in the assurance guide.

Does Writfold post PR comments or Slack messages?

No. kb deliver keeps drafts with their checks in the run. Nothing is sent.

Who accepts a proposal?

You do. kb propose queues a record call locally, and the writfold:evaluate skill may queue up to three. Only proposals accept writes the record, and it is refused when a citation in it is no longer fresh.

Other harnesses?

The CLI works wherever an agent has a shell. An MCP server is deferred until a harness without a shell needs one.

Is the source available?

Yes: Writfold, Weft and Splicery are public, and this website is under the MIT license.
