How it works

Four stages.
A record of each.

Each part below is two sentences, one example and a link to the full guide. The commands are real and all of it runs in the preview; the one planned item is marked.

The base

Records in Git, an index you can rebuild

The knowledge base is a Git repository of plain Markdown and JSON: decisions, tickets, assets, the links between them and one folder per run. Every row of an answer ends in its source, and the last line says what was examined and how many sources are stale.

Stage 1 / Research

Ask the knowledge base, or search the code

The kb verbs answer from what the project already knows, and a short Tuft program finds exact text in code at one pinned commit. With --cite each row carries a citation, and what the agent concludes it writes down with record.

In a run with a plan, a required research step owes backfilled, a check of the run’s own records. It passes only once the step wrote a record, a citation or a retrieval receipt.

→ Full skeleton: what each stage writes back

Stage 2 / Plan

Start a run, set its plan

A run records the task, the repository, branch, worktree and base commit, and plan set copies a template’s steps into it, each step naming the gates it owes. Templates listed in .writfold/plans/required.toml are added to every plan: here a research step at the start and a reflect step at the end.

Writfold records the steps and the agent walks them; it schedules nothing. A template can include another with use=, and the run keeps a snapshot of each, so a template edited later is flagged !template-moved and the run is not rewritten.

Stage 3 / Execute

Edit, check, advance

The agent edits the run’s worktree with Splicery recipes for repeated or structural edits, or with ordinary tools for one small change, and any gate whose scope covers the change is owed again. plan advance records the current step as done only when each of its gates is met; a done step whose gate later goes stale is flagged !stale and stays done.

A skill adds its own steps with one line, plan use; a repeat writes nothing. plan skip --reason TEXT --by WHO closes a step without calling it done.

Two sessions, two clones: every plan write re-checks its decision under the knowledge base’s write lock, and refuses and writes nothing if the plan changed since the command read it. After two clones merge, plan status, resume and kb check flag !out-of-order (a done step after an open one), !two-plans and !repeated and exit 2; they never change the plan. A TLC model of the run graph found both gaps.

Stage 4 / Deliver

Drafts, checked. Nothing sent.

kb deliver prepare copies a PR comment or Slack summary into the run as the exact text that would be posted, and deliver check runs three checks on those bytes: paragraph length, references the audience must not see, and whether every citation is still fresh. Writfold has no network code, so posting stays with you or your agent.

The checks are mechanical: they do not judge tone or truth. An optional Claude Code hook, off unless configured, can deny a listed publishing command until a ready draft holds the exact bytes: a guard, not enforcement.

Before the run ends

Reflect, propose, close

The required reflect step owes two gates: a run-record check that passes only when the run holds a reflection: entry and a proposal or an explicit no proposal, and a statement that the reflection covers what its instructions ask. A proposal is a record call not yet made, kept in a local queue until you accept or drop it.

The bundled writfold:evaluate skill walks this step in a forked subagent and never accepts a proposal itself. The check shows that a reflection was written, not that it is good.

The thread

Who owes a gate, and what meets it

Plan steps, runs and delivery drafts owe gates, and evidence that Writfold records meets them. Gates report; on their own they block nothing (a guard rule can hold a command until they are met); receipts resist mistakes, such as a forgotten check or a stale “tests pass”, and they are tracked files, not signatures.

A step can owe a Weft assessment. The agent states the step’s assumptions and checks in a Weft file and cites evidence for each assumption. A check is met only when Weft entails it from assumptions whose every citation Writfold found fresh or satisfied, which Weft calls a “grounded basis”; otherwise it is shown as hypothetical and does not meet the gate.

Any time

Check that it still holds

The index refreshes itself on every read, so there is no sync step. kb check re-checks the rest in one summary: cited sources, the index against a rebuild, gate evidence, and the plan when the run has one.

In Claude Code

The plan position at session start, drafts at the end

The plugin puts brief, resume, the plan position and an inbox of drafts, proposals and runs that ended without a reflection into a new session with no tool call, and re-injects the plan position after a compaction. It reads local files and refs only, runs no model, and does nothing when the binary or the knowledge base is missing.
