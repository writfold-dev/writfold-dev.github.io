How it works

Small files.
A few commands.

You describe your checks, plans and rules in small files, kept in Git. The agent runs a few commands against them. Here is one short example, then seven files, each beside the commands that use it.

An example

Stop on one machine, resume on another

Six commands, run on a demo repository whose unit gate covers src/**. The output is real and trimmed: … stands for a run ID, a path or lines left out.

  1. 1. Record a decision. It is a file, and the answer names where it is.

    $ writfold kb record decision --title "Batch ledger writes" \
    --target-source src/ledger.rs \
    --why "One transaction per 500 rows keeps replay under a minute."
decision proposal/decision/2026-11-17-batch-ledger-writes [draft] Batch ledger writes @proposals/…/proposal.md:6
…

  2. 2. Start a run, with a note for the next session.

    $ writfold kb checkpoint --new-run --project demo-api \
    --task "batch ledger writes" \
    --note "Batching at 500 rows. Next: tune the batch size."
run run-… [open] batch ledger writes @runs/run-…/manifest.json:8 !current
…
checkpoint 2026-11-17T00:42:26Z entry 1 of 1 @runs/run-…/checkpoint.md:2
  note: Batching at 500 rows. Next: tune the batch size. @runs/run-…/checkpoint.md:4
…

  3. 3. Pass a gate. Its receipt names the commit and the bytes it checked.

    $ writfold kb gate run unit
gate unit [satisfied] mechanical pass exit=0 at demo-api@de2997f4dbc4 scope=7ac784bc428b paths=1 @runs/run-…/gates/unit-….json:1
…

  4. 4. Stop. Commit and push the run’s files.

    $ git add -A && git commit -qm "batch writes: decision, checkpoint, receipt" && git push -q

  5. 5. Later, a commit changes a file in the gate’s scope.

    $ sed -i 's/500/250/' src/ledger.rs && git commit -qam "try 250 rows" && git push -q

  6. 6. On another machine, clone and resume. The gate is stale, and the next: line names the command that meets it again.

    $ git clone -q …/demo-api.git && cd demo-api && writfold kb resume
run run-… [open] batch ledger writes @runs/run-…/manifest.json:8
…
gate unit [stale] mechanical pass exit=0 at demo-api@de2997f4dbc4 scope=7ac784bc428b paths=1 @runs/run-…/gates/unit-….json:1 !stale
  why: changed in scope: src/ledger.rs
  next: writfold kb gate run unit
checkpoint 2026-11-17T00:42:26Z entry 1 of 1 @runs/run-…/checkpoint.md:2
  note: Batching at 500 rows. Next: tune the batch size. @runs/run-…/checkpoint.md:4
…

A gate

A gate is a check that leaves a receipt

This gate runs the unit tests. Its receipt is tied to the files in scope: edit one of them, and the gate is owed again.

  1. Run the check and keep a receipt.

    $ writfold kb gate run unit

  2. See where every gate stands.

    $ writfold kb gate status

  3. Some gates are a statement, not a command. Make one.

    $ writfold kb gate attest wording \
    --statement "README unchanged" --by agent

A plan

A plan is a list of steps and the gates each one owes

Each line is a step name, then its gates. Writfold records the steps. The agent does the work.

  1. Give the current run this plan.

    $ writfold kb plan set fix

  2. See each step and what it owes.

    $ writfold kb plan status

  3. Record the current step as done. Refused while a gate is owed.

    $ writfold kb plan advance

Your policy

Your policy says what counts

You decide what adequate work means; Writfold holds no opinion of its own. Here the research gate takes a statement and no waiver, and every plan starts with a research step that cannot be skipped.

  1. A waiver is refused.

    $ writfold kb gate waive research \
    --reason "no time" --by agent
writfold kb: refused: gate research does not accept a waiver (accept = ["attested"] @.writfold/gates/research.toml:7); meet it: writfold kb gate attest research --statement TEXT --by WHO

  2. So is skipping the step.

    $ writfold kb plan skip \
    --reason "no time" --by agent
step research#1/research [current] owes: research [open] @runs/run-…/plan/splice-research.1.json:1 !locked
  next: writfold kb gate attest research --statement TEXT --by WHO
# note: not skipped: research#1/research is a required step this run cannot skip (unskippable = ["research"] @.writfold/plans/required.toml:3, pinned @runs/run-…/policy/pin-1-….json:1); nothing written
…

  3. A finished plan says how it finished. This one closed its research on a statement and skipped two steps.

    $ writfold kb plan status
…
plan complete-with-exceptions 4 steps: 1 passed, 1 attested, 0 waived, 2 skipped; policy=same @runs/run-…/plan/
…

A skill

A skill adds its own steps

A Claude Code skill can carry one line that adds steps to the plan when the skill loads. The steps come from a template of their own.

  1. The skill’s line. It adds the review steps before the current step; running it twice adds them once. The agent then walks them like any other step.

    $ writfold kb plan use review

A guard rule

A guard rule holds a command until the gates are met

With the Claude Code plugin, this rule denies git commit and git push while the run owes a gate. It only sees the commands Claude Code shows it, so it is a guard, not a lock.

  1. Ask what each rule would decide right now.

    $ writfold kb guard status

  2. A denial names what is owed and the command that meets it. For example:

    $ writfold kb gate run unit

A delivery mode

A delivery mode checks a draft before you send it

This mode checks a commit message. Writfold checks the exact text and sends nothing: posting stays with you or your agent.

  1. Keep the exact text as a draft in the run.

    $ writfold kb deliver prepare \
    --mode commit-message \
    --audience external --from msg.txt

  2. Run the mode’s checks on that text. The draft is ready only when every check is met.

    $ writfold kb deliver check

  3. A plan step can owe this mode: commit: deliver:commit-message. It advances only once the draft is ready.

    $ writfold kb plan advance

A checkpoint

A checkpoint is a note for the next session

Each run keeps its notes in one Markdown file. The next session reads the last ones instead of the whole history.

  1. Write a note into the current run.

    $ writfold kb checkpoint --note \
    "unit passes. Next: attest wording, then commit."

  2. See where the run stopped: its last notes, plan step and owed gates.

    $ writfold kb resume

  3. See where the project stands. The plugin adds this at session start.

    $ writfold kb brief
