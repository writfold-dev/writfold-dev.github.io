How it works

Four stages.
A record of each.

Each part is two sentences, one example and a link to its guide. Everything runs in the preview; the one planned item is marked.

The base

Records in Git, checked on demand

The knowledge base is a Git repository of Markdown and JSON: decisions, tickets, assets, their links and one folder per run. Every row of an answer ends in its source, and kb check re-checks citations, the index, gate evidence and the plan in one summary.

Stage 1 / Research

Ask the knowledge base, or search the code

The kb verbs answer from what the project already knows, and a Tuft search finds exact text in code at one pinned commit. With --cite each row carries a citation, and in a run with a plan the required research step passes only once it wrote a record, a citation or a retrieval receipt.

→ Full skeleton: what each stage writes back

Stage 2 / Plan

Start a run, set its plan

A run records the task, the repository, branch, worktree and base commit, and plan set copies a template’s steps into it. Each step names the gates it owes; Writfold records the steps and schedules nothing.

→ Full skeleton: the run graph

The thread

Who owes a gate, and what meets it

A gate is a command with the paths it covers, a statement someone makes, or a check of the run’s own records. Evidence is tied to exact bytes, so a change makes the gate owed again; gates report and block nothing on their own, and receipts are tracked files, not signatures.

A step can also owe a Weft assessment, met only when the check is entailed from assumptions whose citations hold.

→ Full skeleton: every gate class, with examples and what is proved, tested and trusted

Stage 3 / Execute

Edit, check, advance

The agent edits the run’s worktree with Splicery recipes or ordinary tools, and any gate whose scope covers the change is owed again. plan advance records the current step as done only when each of its gates is met, and a skill adds its own steps with plan use.

A done step whose gate later goes stale is flagged !stale and stays done. plan skip --reason TEXT --by WHO closes a step without calling it done.

→ Full skeleton: steps, splicing, stale and merged clones and skills that splice

Watching the run

The plan as a map

writfold watch draws the run’s plan in a terminal, with skills spliced in as nested groups and an inspector for the selected step. It opens calm: text only on the next step and the selected row. d shows every detail, receipts included, and ? holds the marks. Every state comes from a kb verb; there is no key that writes, and it never starts a check.

▶ marks the recorded position, not a claim that an agent is working; the view adds no percentage or time estimate.

→ Keys, layouts, refresh and themes: watching a run

Stage 4 / Deliver

Drafts, checked. Nothing sent.

kb deliver prepare keeps the exact text of a PR comment or Slack summary in the run, and deliver check checks those bytes: paragraph length, references the audience must not see, and whether every citation is still fresh. Writfold has no network code, so posting stays with you or your agent.

The checks are mechanical: they do not judge tone or truth. An optional Claude Code hook, off unless configured, can deny a listed publishing command until a ready draft holds the exact bytes: a guard, not enforcement.

Before the run ends

Reflect, propose, close

The required reflect step passes only when the run holds a reflection: entry and a proposal or an explicit no proposal. A proposal is a record call not yet made, and only you accept it.

The check shows that a reflection was written, not that it is good. The bundled writfold:evaluate skill can walk this step and never accepts a proposal itself.

In Claude Code

The plan position at session start

The plugin puts the brief, the plan position and an inbox into a new session with no tool call, and the plan position again after a compaction. It reads local files and refs only and runs no model.
