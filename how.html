How it works

Four stages.
A record of each.

Each part below is two sentences, one example and a link to the full guide. The commands are real; what is planned is marked.

The base

Records in Git, an index you can rebuild

The knowledge base is a Git repository of plain Markdown and JSON: decisions, tickets, assets, the links between them and one folder per run. Every row of an answer ends in its source, and the last line says what was examined and how many sources are stale.

Stage 1 / Research

Ask the knowledge base, or search the code

The kb verbs answer from what the project already knows, and a short Tuft program finds exact text in code at one pinned commit. With --cite each row carries a citation, and what the agent concludes it writes down with record.

Planned A required step whose check is met only when research wrote something back.

→ Full skeleton: what each stage writes back

Stage 2 / Plan

Start a run

A run records the task, the repository, branch, worktree and base commit, and today the plan is its first checkpoint note. kb resume shows it to any later session.

Planned The run graph. A plan becomes an ordered list of steps, each naming the gates it owes; plan advance moves on only when they are met, and a skill can add its own steps. Writfold records the steps and the agent walks them. Required steps, such as a closing reflection, are part of every run, and a step can ask for a Weft assessment.

→ Full skeleton: the run graph (planned)

Stage 3 / Execute

Edit, check, checkpoint

The agent edits the run’s worktree with Splicery recipes for repeated or structural edits, or with ordinary tools for one small change. Either way the result is an uncommitted Git change, and any gate whose scope covers it is owed again.

→ Full skeleton: gate definitions, receipts and standing

Stage 4 / Deliver

Drafts, checked. Nothing sent.

kb deliver prepare copies a PR comment or Slack summary into the run as the exact text that would be posted, and deliver check runs three checks on those bytes: paragraph length, references the audience must not see, and whether every citation is still fresh. Writfold has no network code, so posting stays with you or your agent.

The checks are mechanical: they do not judge tone or truth. An optional Claude Code hook, off unless configured, can deny a listed publishing command until a ready draft holds the exact bytes: a guard, not enforcement.

→ Full skeleton: delivery modes, deny lists and the guard

The thread

Who owes a gate, and what meets it

Runs and delivery drafts owe gates, and evidence that Writfold records meets them. Gates report and block nothing; receipts resist mistakes, such as a forgotten check or a stale “tests pass”, and they are tracked files, not signatures.

→ Full skeleton: what is proved, tested and trusted

Any time

Check that it still holds

The index refreshes itself on every read, so there is no sync step. Three commands re-check the rest on demand: cited sources, the index against a rebuild, and gate evidence.

Planned kb check, one command for all three.

In Claude Code

A brief at session start, drafts at the end

The plugin puts brief and resume into a new session with no tool call, and keeps a local checkpoint draft at compaction and stop. One skill teaches the verbs; the hooks run no model, and a missing binary or knowledge base makes them do nothing.
