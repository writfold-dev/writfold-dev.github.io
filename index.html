Git-native project continuity for coding agents

Project memory
that travels with Git.

Writfold's direction is project continuity for coding agents. A fresh agent session, on any machine, should be able to answer “why did we decide X”, “where do we stand on Y”, “what is the tracker item for Z” and “what does changing X touch”. Every answer is pinned to a source, a path at a commit with a digest, and flagged when that source has moved.

The problem: every new agent session starts from nothing, and what it reads about past decisions may already be out of date. Writfold keeps project memory as plain records in Git, so moving to another machine is git clone or git pull. One static binary, no server. None of this is built yet: it is the plan, and the first slice is next.

The core idea

Found, supported, approved: three different things.

Finding a record does not make it right, and a record is not a decision until it is accepted. Writfold keeps those as separate facts, and says when a source has moved since an answer relied on it.

What runs today · frozen working demo

The edit trial, six steps

Before the change of direction, Writfold was built as an evidence-and-approval layer for agent edits. That cooperating single-user trial still builds and runs end to end on any Git repository, as a working demo; it gets no new development. In it, Writfold is the owner: it alone holds the store and alone changes files. Weft and Splicery only read and propose, and also run as standalone tools.

  1. 01 / Writfold

    Retain exact inputs

    Keep the exact bytes of a file at a full commit id, bound as a citation by digest, so later edits cannot rewrite the evidence.

    Runs (trial)
  2. 02 / Weft

    Assess the claims

    Check what the declared assumptions actually support: entailed, refuted or still open. A report citing evidence that was not retained is refused.

    Runs today
  3. 03 / Splicery

    Prepare an edit

    Describe a byte-exact change and compute a candidate file. The original stays untouched.

    Runs today
  4. 04 / Writfold

    Approve that edit

    You sign an approval bound to this exact prepared change, checked against a current operator grant and the context's policy.

    Runs (trial)
  5. 05 / Writfold

    Apply it

    Writfold writes the approved change into its own Git worktree, after re-checking the file has not changed.

    Runs (trial)
  6. 06 / Writfold

    Record the outcome

    A durable claim before the write and one recorded outcome after it. After an interrupted apply, recover decides the outcome from the file's exact bytes instead of applying the edit twice.

    Runs (trial)

Try it

Build and run from source

A source-only preview: there is no installer or release binary. Linux x86_64 with rustup; the pinned toolchain installs on first build. These are the commands from the Writfold README, at tag v0.1.0-dev.1. They run the frozen working demos; nothing of the continuity direction is built yet.

# In a clone of https://github.com/writfold-dev/writfold
cargo build --release -p writfold

# Prepare, approve and apply one edit
export WRITFOLD_STATE=/tmp/writfold-trial
target/release/writfold trial init
target/release/writfold trial prepare --repo /path/to/repo --file src/lib.rs --recipe edit.spl
target/release/writfold trial approve <run>
target/release/writfold trial apply <run>
git -C "$WRITFOLD_STATE/worktrees/<run>" diff

# Find and cite exact evidence with Tuft
printf '@h := find text "trial_blob(" in "crates/" at "%s";\n@e := retain @h around lines 0;\n@v := project @e [path, line, binding, excerpt(max_chars: 72)] limit 6;\nemit @v budget_tokens 300;\n' "$(git rev-parse HEAD)" > q.tuft
target/release/writfold tuft run q.tuft --repo .

Your own checkout is never written: Writfold makes its own sparse worktree of the repository's HEAD, replays a Splicery recipe through the pinned kernel, and installs the result only after a signed approval and a current grant are verified. apply records a durable claim before it touches the file, and writfold trial recover <run> settles an interrupted apply. Splicery's examples/try/ has a recipe for a small Rust file; trial retain and approve --require CHECK are described in the trial profile. Weft and Splicery each have their own Try it: Weft, Splicery.

This is a cooperating single-user trial. It never writes your checkout, but nothing stops an agent's own shell from doing so, and it assumes nobody races it on its worktree. Search is exact text or a bounded regex. Fuzzy (typo-tolerant) text search is planned in the local rebuildable index.

Working demos: the edit trial and Tuft

A cooperating single-user trial, end to end on any Git repository: retain exact evidence (or find it with Tuft), bind a Weft report, prepare a Splicery edit in Writfold's own sparse worktree, approve, apply and recover, every step in a durable, validated ledger. serve exposes show, retain, prepare, the one-command run and evidence reads; approval stays CLI-only. Every trial operation's p95 is under 0.5 s on a 100,000-file repository. These still build and run, and get no new development.

Proved over the shipped Rust: the ledger, grant, revocation, recovery-outcome, required-check and edit-flow decisions, plus Weft's set and verdict decisions and Splicery's edit rendering. How we know

Planned

Project continuity

Nothing of the new direction is built yet. Project memory is planned as plain records in Git plus a local index that can always be rebuilt, with fuzzy text search in that index. Paused: the Dolt and Omnigraph backends, and benchmarking. No measured token win: in five pilots the Writfold or Tuft arm used between 1.7% and 16% more tokens than ordinary tools at equal correctness, and in two reliability rounds ordinary tools on a smaller model were already right 23 times in 24.
