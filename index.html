An evidence-and-approval harness for coding agents

Another take on
the agent harness.

Writfold is for people running coding agents on real repositories. Your agent, such as Claude Code or Codex, stays the loop. Writfold is designed to sit underneath it and govern what the agent may know, conclude and change, keeping evidence of every step.

The problem: agents act on context nobody verified, and leave edits nobody can review or replay. Writfold keeps knowledge for reasoning, Weft checks the plan, Splicery expresses the edit, and only Writfold applies it, in a Git worktree it owns.

How the pieces fit

Know, conclude, change, record

Writfold does not replace the agent loop or the model. It is the layer the agent goes through for knowledge it relies on and for every change it makes to your files.

  1. Know / Writfold

    Exact, cited evidence

    Writfold retains the exact bytes and revision behind what the agent read, in a named context. A finding is not a proof, and a citation is not an approval.

    Parts tested
  2. Conclude / Weft

    Check the plan

    Weft checks a plan's claims against declared assumptions and evidence: each is entailed, refuted or still open. Its reports carry no permission to change anything.

    Runs today
  3. Change / Splicery + Writfold

    Edit only where owned

    Splicery expresses a byte-exact edit recipe and previews the candidate. Writfold applies it only in a Git worktree it created, under your signed approval and a current operator grant.

    Runs (trial profile)
  4. Record / Writfold

    Evidence at every step

    Each step leaves a receipt, so a run can be reviewed afterwards, recovered after a crash, or reused by the next session.

    Planned

The core idea

Found, supported, approved: three different things.

Finding a document does not make it right, and a document being right is not permission to act on it. Writfold records each of those as a separate step.

The same holds across contexts: evidence or approval in one context never silently authorizes anything in another.

One edit, end to end

The six steps

Writfold is the owner: it alone holds the knowledge store and alone changes files. Weft and Splicery only read and propose. Steps 2 and 3 run today as standalone tools; the rest are being built.

  1. 01 / Writfold

    Retain exact inputs

    Keep the source bytes, revision and identity inside a named context, so later edits cannot rewrite the evidence.

    Parts tested
  2. 02 / Weft

    Assess the claims

    Check what the declared assumptions actually support: entailed, refuted or still open.

    Runs today
  3. 03 / Splicery

    Prepare an edit

    Describe a byte-exact change and compute a candidate file. The original stays untouched.

    Runs today
  4. 04 / Writfold

    Approve that edit

    You sign an approval bound to this exact prepared change, checked against a current operator grant and the context's policy.

    Runs (trial)
  5. 05 / Writfold

    Apply it

    Writfold writes the approved change into its own Git worktree, after re-checking the file has not changed.

    Runs (trial)
  6. 06 / Writfold

    Record a receipt

    Keep a durable receipt. If a response is lost, recover the same result instead of applying the edit twice.

Three tools

Three tools, one approval boundary

Each tool has one job. Only Writfold can change anything.

Writfold

Stores exact evidence, holds the approval policy, and is the only component that writes files or publishes knowledge.

writfold serveToday: the trial prepare → approve → apply flow, and a stdio session. Source

Weft

A small language for stating assumptions and checks, then reporting which checks follow. Its reports carry no write permission.

Splicery

A small language for byte-exact edits. It computes a candidate file and never touches the original.

Try it

Build and run from source

Linux x86_64 with rustup. Each repository pins its Rust toolchain, which installs on first build.

# Splicery: preview a byte-exact edit to a Rust file
git clone https://github.com/writfold-dev/splicery
(cd splicery && cargo build --release --locked)
(cd splicery/examples/try && ../../target/release/splicery-cli preview --root . --file client.rs add-retry.spl)

# Weft: check what declared assumptions support
git clone https://github.com/writfold-dev/weft
(cd weft && cargo build --release --locked && target/release/weft prove examples/sets.weft --human)

# Writfold: prepare, approve and apply that edit in Writfold’s own worktree of splicery
git clone https://github.com/writfold-dev/writfold
(cd writfold && cargo build --release -p writfold)
export WRITFOLD_STATE=/tmp/writfold-trial
writfold/target/release/writfold trial init
writfold/target/release/writfold trial prepare --repo splicery \
  --file examples/try/client.rs --recipe writfold/examples/trial/add-retry.spl
writfold/target/release/writfold trial approve <run>
writfold/target/release/writfold trial apply <run>
git -C "$WRITFOLD_STATE/worktrees/<run>" diff

Status

What runs today

Runs

Tools and tested parts

The Weft and Splicery examples on this site run with development binaries. The writfold binary starts a stdio session and refuses everything else. Separately tested parts cover exact object storage, an Omnigraph data path, Git worktree creation, procedure checking, signed edit approval, operator grants and a validated ledger.

Test record: 12 real-process scenarios across 29 invocations, plus 8 coverage tests.

Not yet

The connected flow

The parts are not yet connected, so the six steps cannot run end to end. Four scenarios that need those services stay blocked: shared evidence handoff, approved edits, crash recovery and session benchmarks.

The next milestone is an experimental alpha for disposable data only.
